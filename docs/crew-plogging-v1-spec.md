# 크루 및 같이 플로깅하기 V1 기능 명세

## 문서 목적

이 문서는 Plover-BE에 크루 및 같이 플로깅하기 기능을 추가하기 위한 기능 명세이다.

구현자는 실제 코드를 수정하기 전에 이 문서를 전체적으로 읽고,
현재 프로젝트의 코드 구조와 기존 개인 플로깅 기능을 먼저 분석해야 한다.

이 문서에 작성된 엔티티명, 테이블 구조, API 경로는 예시이며
현재 프로젝트 구조와 맞지 않을 경우 기존 코드 스타일에 맞게 조정할 수 있다.

단, 아래의 핵심 정책은 임의로 변경하지 않는다.

## 변경할 수 없는 핵심 정책

- 개인 플로깅 기록은 사용자별로 독립적으로 저장한다.
- 개인 기록에는 본인의 기록과 본인이 촬영한 사진만 포함한다.
- 같이 플로깅 활동 한 번당 크루 기록은 한 건만 표시한다.
- 크루 기록의 거리, 걸음 수, 시간은 대표 개인 기록을 기준으로 한다.
- 참가자들의 거리, 걸음 수, 시간을 합산하지 않는다.
- 대표 기록은 크루장 기록을 우선 사용한다.
- 크루장 기록이 없다면 정상 완료한 참가자 중 가장 먼저 완료한 기록을 사용한다.
- 크루 기록에는 참가자들이 촬영한 사진 전체를 표시한다.
- 사진은 기존 Presigned URL API를 이용해 S3에 한 번만 업로드한다.
- 동일한 사진을 개인 기록과 크루 공유 기록에서 논리적으로 참조한다.
- 공유 사진 업로드는 해당 같이 플로깅 세션 참가자만 가능하다.
- 공유 사진 조회는 현재 크루에 소속된 모든 크루원에게 허용한다.
- 크루 기록을 통해 참가자의 개인 경로, 리포트, 경험치를 공개하지 않는다.
- MVP에서는 폴링 방식으로 시작 및 종료 상태를 확인한다.
- 기존 코드와 관계없는 대규모 리팩터링은 하지 않는다.


# 크루 및 같이 플로깅하기 1차 기능 명세

## 1. 구현 목표

현재 Plover-BE 프로젝트에 다음 기능을 구현한다.

1. 크루 생성
2. 참여 코드를 이용한 크루 참가
3. 내가 소속된 크루 목록 조회
4. 크루 상세 조회
5. 같이 플로깅 세션 생성·참가·시작·종료
6. 참가자별 개인 플로깅 기록 저장
7. 크루 같이 플로깅 기록 생성
8. 기존 사진 업로드 기능을 활용한 크루 사진 공유

이번 MVP에서는 다음 기능을 구현하지 않는다.

- 가입 승인
- 크루장 위임
- 크루 삭제
- 크루원 강퇴
- 실시간 위치 공유
- 참가자별 거리 또는 기록 비교
- 크루 순위
- AI 추천 경로
- WebSocket, SSE, FCM 등 신규 실시간 인프라

기존 프로젝트의 인증 방식, 패키지 구조, 공통 응답, 예외 처리, 개인 플로깅 완료 로직 및 S3 Presigned URL 방식을 최대한 재사용한다.

정확한 엔티티 구조와 API 경로는 먼저 현재 코드베이스를 분석한 후 기존 설계에 맞게 결정한다.

---

# 2. 기록의 핵심 원칙

## 개인 플로깅 기록

같이 플로깅에 참가한 사용자도 기존 개인 플로깅과 동일하게 각자의 개인 기록을 저장한다.

개인 기록에는 본인의 정보만 저장하고 조회한다.

- 본인의 이동 경로
- 본인의 이동 거리
- 본인의 걸음 수
- 본인의 플로깅 시간
- 본인의 경험치
- 본인의 리포트
- 본인이 촬영한 사진

크루장이 같이 플로깅을 진행했더라도 크루장의 개인 기록에는 다른 참가자가 촬영한 사진을 포함하지 않는다.

```text
크루장 개인 기록
= 크루장 개인 측정 기록 + 크루장이 촬영한 사진

크루원 개인 기록
= 해당 크루원의 개인 측정 기록 + 해당 크루원이 촬영한 사진
```

---

## 크루 같이 플로깅 기록

한 번의 같이 플로깅 활동당 크루 기록은 한 건만 생성한다.

크루 기록은 다음 정보로 구성한다.

```text
대표 개인 플로깅 기록의 요약 정보
+
같이 플로깅 참가자들이 촬영한 전체 사진
```

크루 기록에는 참가자들의 거리, 걸음 수, 시간을 합산하지 않는다.

크루 기록에서 사용하는 대표 기록은 다음 우선순위로 결정한다.

1. 크루장이 정상적으로 저장한 개인 플로깅 기록
2. 크루장 기록이 없다면 정상 완료한 참가자 중 가장 먼저 완료된 개인 플로깅 기록
3. 정상 완료된 개인 기록이 하나도 없다면 대표 기록 없는 세션으로 처리하고 크루 통계에서 제외

대표 기록을 통해 크루 기록에 보여주는 정보는 다음으로 제한한다.

- 플로깅 날짜
- 시작 및 종료 시각
- 걸음 수
- 이동 거리
- 플로깅 시간
- 대표 사용자 닉네임

다음 정보는 크루 기록에서 제공하지 않는다.

- 대표 사용자의 개인 리포트
- 대표 사용자의 경험치 상세
- 대표 사용자의 개인 이동 경로
- 참가자별 걸음 수
- 참가자별 거리
- 참가자별 시간
- 참가자별 경험치
- 참가자별 개인 리포트

다른 사용자가 대표 개인 기록의 원본 상세 API에 접근하게 하지 말고, 크루 기록 전용 응답을 통해 허용된 요약 정보만 반환한다.

# 3. 크루 생성

사용자가 크루명을 입력해 크루를 생성한다.

- 크루명 중복을 허용한다.
- 생성자는 자동으로 해당 크루의 크루장으로 등록한다.
- 생성자는 크루원 목록에도 포함한다.
- 한 사용자는 여러 크루를 생성하거나 참가할 수 있다.

크루 생성 시 참여 코드를 함께 생성한다.

## 참여 코드 규칙

- 영문 대문자 `A-Z`
- 숫자 `0-9`
- 총 8자리
- 모든 크루에서 유일해야 함
- 만료 기간 없음
- 하나의 크루에 영구 귀속
- MVP에서는 코드 재발급 기능 없음
- 서버 저장 및 비교 시 대문자로 정규화

예시:

```text
A7K9P2X4
9QR2B8NM
```

참여 코드가 이미 존재하면 새로운 랜덤 코드를 다시 생성한다.

크루에 소속된 모든 현재 크루원은 크루 상세 화면에서 참여 코드를 확인하고 복사할 수 있다.

크루장이 아닌 일반 크루원도 참여 코드를 조회할 수 있다.

---

# 4. 크루 참가

사용자는 크루 목록 화면에서 `크루 들어가기` 버튼을 누르고 8자리 참여 코드를 입력한다.

유효한 참여 코드라면 별도의 가입 승인 없이 즉시 가입한다.

참가 시 다음을 검증한다.

- 참여 코드 형식이 올바른지
- 해당 참여 코드의 크루가 존재하는지
- 사용자가 현재 이미 해당 크루에 소속되어 있는지
- 사용자가 과거 해당 크루에서 탈퇴한 상태인지

현재 이미 가입된 사용자가 동일 크루에 재가입을 요청하면 가입을 차단한다.

예외 코드 예시:

```text
ALREADY_CREW_MEMBER
```

과거 탈퇴했던 사용자는 동일한 참여 코드를 통해 다시 가입할 수 있다.

재가입 구현 방식은 현재 프로젝트 구조를 분석한 후 선택한다.

- 기존 멤버십을 활성 상태로 복구하거나
- 가입 이력을 유지하면서 새 활성 멤버십을 생성할 수 있음

다만 다음 조건은 반드시 지킨다.

- 동일 크루에 활성 멤버십이 중복되지 않을 것
- 탈퇴 사용자의 재가입을 허용할 것
- 재가입 후 과거 크루 기록과 공유 사진을 조회할 수 있을 것

크루 탈퇴 API 자체는 이번 1차 MVP 구현 대상에서 제외할 수 있다. 다만 향후 탈퇴와 재가입이 가능하도록 확장 가능한 구조로 설계한다.

---

# 5. 내가 소속된 크루 목록 조회

로그인 사용자가 현재 소속된 크루 목록을 조회할 수 있어야 한다.

각 크루 항목에는 다음 정보를 제공한다.

- 크루 ID
- 크루명
- 현재 크루원 수
- 로그인 사용자의 역할
- 완료된 크루 플로깅 횟수
- 총 누적 걸음 수
- 총 누적 거리
- 총 누적 시간
- 활성 같이 플로깅 세션 존재 여부
- 활성 세션 상태

탈퇴 상태의 크루는 목록에서 제외한다.

## 크루 통계 기준

크루 통계는 참가자 전체의 수치를 합산하지 않는다.

각 크루 같이 플로깅 세션의 대표 개인 기록을 기준으로 계산한다.

```text
플로깅 횟수
= 대표 기록이 존재하는 완료된 크루 플로깅 세션 수

총 누적 걸음 수
= 각 크루 플로깅 대표 기록의 걸음 수 합계

총 누적 거리
= 각 크루 플로깅 대표 기록의 이동 거리 합계

총 누적 시간
= 각 크루 플로깅 대표 기록의 플로깅 시간 합계
```

대표 기록은 크루장 개인 기록을 우선 사용한다.

크루장 개인 기록이 없으면 정상 완료한 참가자 중 가장 먼저 완료한 개인 기록을 사용한다.

다음 세션은 통계에서 제외한다.

- 참가자 모집 중인 세션
- 진행 중인 세션
- 시작 전 취소된 세션
- 정상 저장된 개인 기록이 하나도 없는 세션

통계 저장 방식을 미리 고정하지 않는다.

현재 프로젝트 및 예상 데이터 양을 분석하여 조회 시 집계하거나 별도의 통계 저장 방식을 선택한다.

---

# 6. 크루 상세 조회

현재 해당 크루에 가입되어 있는 사용자만 크루 상세를 조회할 수 있다.

응답에는 다음 정보를 포함한다.

- 크루 ID
- 크루명
- 참여 코드
- 현재 크루원 수
- 크루원 목록
- 로그인 사용자의 역할
- 로그인 사용자가 크루장인지 여부
- 완료된 크루 플로깅 횟수
- 총 누적 걸음 수
- 총 누적 거리
- 총 누적 시간
- 활성 같이 플로깅 세션 정보
- 완료된 크루 플로깅 기록 목록

크루원 목록에는 현재 프로젝트에 존재하는 사용자 필드만 사용해 다음 정보를 제공한다.

- 사용자 ID
- 닉네임
- 프로필 이미지
- 역할

모든 현재 크루원은 참여 코드를 조회할 수 있다.

---

# 7. 같이 플로깅 세션 생성

크루 상세 화면에서 크루장만 `같이 플로깅하기` 버튼을 누를 수 있다.

일반 크루원은 세션을 생성할 수 없다.

크루장이 버튼을 누르면 참가자를 모집하는 활성 세션을 생성한다.

세션 생성 시 크루장은 자동으로 참가자로 등록한다.

하나의 크루에는 참가자 모집 중이거나 진행 중인 활성 세션이 동시에 하나만 존재해야 한다.

크루장만 생성할 수 있더라도 다음 상황을 고려해 서버에서 중복 생성을 방지한다.

- 버튼 중복 클릭
- 네트워크 재시도
- 동일 계정의 여러 기기 사용
- 동일 요청의 중복 전송

중복 생성 요청에서는 세션이 두 건 생성되지 않도록 트랜잭션, DB 제약 또는 현재 프로젝트에 적합한 동시성 처리 방식을 적용한다.

---

# 8. 같이 플로깅 참가

일반 크루원은 참가자 모집 상태의 활성 세션에서 `참가하기` 버튼을 누를 수 있다.

참가 조건:

- 현재 해당 크루에 가입된 사용자
- 세션이 참가자 모집 상태
- 아직 해당 세션에 참가하지 않은 사용자

크루장은 세션 생성 시 자동으로 참가 처리한다.

크루장이 시작하기 전에는 일반 크루원이 참가를 취소할 수 있다.

크루장은 참가를 취소할 수 없다.

세션이 시작된 이후에는 다음을 허용하지 않는다.

- 신규 참가
- 참가 취소

같은 참가 요청이 여러 번 전달되더라도 참가 데이터가 중복 생성되지 않도록 한다.

---

# 9. 같이 플로깅 시작

크루장만 같이 플로깅을 시작할 수 있다.

시작 시 서버는 다음을 처리한다.

- 세션을 진행 상태로 변경
- 서버 기준 공통 시작 시각 저장
- 신규 참가 차단
- 참가 취소 차단

같이 플로깅은 AI 경로 추천 없이 자유 경로로 진행한다.

참가자 앱은 활성 세션을 약 2~3초 간격으로 폴링한다.

세션이 진행 상태로 변경된 것을 확인하면 기존 개인 플로깅 화면으로 이동한다.

각 참가자의 기기는 기존 개인 플로깅과 동일하게 다음 정보를 독립적으로 측정한다.

- GPS 위치
- 이동 경로
- 이동 거리
- 걸음 수
- 플로깅 시간
- 촬영한 사진

참가자들의 실시간 위치와 이동 경로는 서로 공유하지 않는다.

---

# 10. 같이 플로깅 중 사진 촬영 및 업로드

같이 플로깅 중 사진 촬영은 현재 개인 플로깅에서 사용하는 기존 Presigned URL 업로드 기능을 그대로 사용한다.

기존 API:

```http
POST /api/plogging-sessions/photo/upload-url?contentType={contentType}
```

지원 MIME 타입은 기존 정책을 따른다.

```text
image/jpeg
image/png
image/webp
image/heic
image/heif
image/avif
```

응답 예시:

```json
{
  "uploadUrl": "https://...presigned-put-url...",
  "objectUrl": "https://...s3-object-url..."
}
```

## 클라이언트 사진 처리 흐름

1. 사용자가 플로깅 도중 사진을 촬영한다.
2. 기존 업로드 URL 발급 API를 호출한다.
3. 응답받은 `uploadUrl`로 S3에 `PUT` 요청을 보낸다.
4. 업로드가 성공하면 `objectUrl`을 클라이언트의 현재 플로깅 상태에 보관한다.
5. 개인 플로깅 완료 요청 시 본인이 촬영한 `objectUrl` 목록을 서버에 전달한다.
6. 서버는 해당 사진들을 사용자의 개인 플로깅 사진으로 저장한다.
7. 같이 플로깅 참가자의 기록이라면 동일한 사진들을 해당 크루 같이 플로깅 세션의 공유 사진으로도 연결한다.

사진 한 장을 개인 기록과 크루 기록에 사용하기 위해 S3에 두 번 업로드하지 않는다.

동일한 S3 객체를 다음 두 곳에서 논리적으로 참조한다.

```text
본인의 개인 플로깅 사진
+
같이 플로깅 세션 공유 사진
```

정확한 DB 구조는 현재 개인 사진 저장 방식을 분석한 뒤 결정한다.

가능한 방식의 예:

- 기존 개인 사진 레코드를 크루 공유 관계에서도 참조
- 동일한 `objectUrl`을 사용하는 별도의 크루 사진 연결 정보 저장
- 하나의 사진 레코드가 개인 기록과 크루 세션을 함께 참조

특정 구조를 미리 강제하지 말고 기존 코드와 가장 자연스럽게 통합한다.

단, 개인 사진과 크루 공유 사진의 조회 권한 및 역할은 논리적으로 분리한다.

---

# 11. 사진 업로드 검증

기존 업로드 URL API와 사진 저장 로직을 분석하고 가능한 기존 검증을 재사용한다.

사진 등록 시 최소한 다음을 검증한다.

- 지원하는 이미지 MIME 타입인지
- 허용된 파일 확장자인지
- 허용된 파일 크기인지
- 현재 서비스에서 사용하는 S3 버킷의 URL인지
- 허용된 S3 경로인지
- 인증 사용자가 제출한 사진인지
- 같이 플로깅 사진이라면 해당 사용자가 실제 세션 참가자인지

클라이언트가 임의의 외부 이미지 URL을 개인 기록이나 크루 기록에 등록하지 못하도록 한다.

기존 `objectUrl` 저장 방식이 URL 신뢰성 검증을 하지 않는다면 현재 프로젝트 구조를 분석한 후 최소한 버킷 호스트와 객체 경로를 검증한다.

기존 Presigned URL의 S3 객체 경로가 사용자 ID 또는 다른 소유 정보를 포함한다면 해당 규칙을 유지하고 활용한다.

새로운 크루 전용 사진 업로드 URL API는 반드시 만들 필요가 없다.

기존 API로 요구사항을 충족할 수 있다면 해당 API를 그대로 재사용한다.

---

# 12. 개인 플로깅 완료 및 기록 저장

같이 플로깅 참가자의 개인 기록 저장은 기존 개인 플로깅 완료 로직을 재사용하거나 최소한으로 확장한다.

개인 플로깅 완료 요청에서 현재 활동이 같이 플로깅인지 식별할 수 있어야 한다.

이를 위해 기존 요청 DTO에 같이 플로깅 세션 식별 정보를 선택적으로 추가하거나, 현재 코드 구조에 적합한 다른 연결 방식을 사용한다.

일반 개인 플로깅에서는 같이 플로깅 세션 정보가 없다.

같이 플로깅 완료 요청에서는 서버가 다음을 검증한다.

- 인증 사용자가 해당 크루 플로깅 세션 참가자인지
- 해당 세션이 실제로 시작된 상태인지
- 해당 사용자가 이미 개인 완료 처리를 하지 않았는지
- 전달된 사진이 해당 사용자가 촬영하고 업로드한 사진인지
- 요청의 사용자 ID가 아닌 인증된 사용자를 기준으로 처리하는지

완료 처리 시 다음을 수행한다.

1. 기존 방식으로 사용자의 개인 플로깅 기록 저장
2. 개인 기록에 본인의 사진만 저장
3. 같이 플로깅 참가 상태 또는 기록 연결 정보 갱신
4. 본인이 촬영한 동일한 사진을 크루 같이 플로깅 공유 사진으로 연결
5. 대표 기록 후보 갱신

개인 기록 저장과 크루 참여 정보 연결은 가능한 한 하나의 트랜잭션에서 처리한다.

동일한 완료 요청이 여러 번 전달돼도 개인 기록과 사진 연결이 중복 생성되지 않도록 한다.

---

# 13. 크루장 전체 종료

크루장이 `같이 플로깅 종료하기` 버튼을 누르면 전체 세션 종료를 요청한다.

서버는 다음을 처리한다.

- 서버 기준 공통 종료 시각 저장
- 세션이 더 이상 진행 중이 아님을 표시
- 신규 참가 차단
- 신규 참가 취소 차단

다른 참가자의 기기를 서버에서 직접 종료할 수는 없으므로 참가자 앱은 폴링으로 종료 상태를 감지한다.

종료 상태를 감지한 앱은 다음 순서로 처리한다.

1. GPS 및 걸음 측정 중지
2. 아직 업로드되지 않은 사진 업로드 완료
3. 개인 플로깅 완료 요청
4. 개인 기록 저장
5. 본인 사진의 개인 기록 및 크루 공유 연결

네트워크가 끊긴 참가자나 백그라운드 상태의 사용자는 재접속 후 종료 상태를 감지하고 개인 완료 요청을 보낼 수 있어야 한다.

크루장이 종료 요청을 보냈다는 이유로 참가자의 개인 기록 저장을 즉시 차단하지 않는다.

종료 후 일정 시간 동안 미제출 참가자의 개인 완료 요청과 사진 등록을 허용한다.

허용 시간은 하드코딩하지 말고 설정값 또는 상수로 관리한다.

---

# 14. 대표 기록 결정

세션 종료 후 정상 저장된 개인 기록 중 대표 기록을 선택한다.

선정 규칙:

```text
1순위: 크루장의 정상 완료 개인 기록
2순위: 크루장 기록이 없으면 가장 먼저 정상 완료된 참가자 개인 기록
3순위: 정상 완료 기록이 없다면 대표 기록 없음
```

참가자 기록이 임시 대표 기록으로 선택된 후 허용 시간 안에 크루장 기록이 도착하면 최종 완료 전에 크루장 기록을 대표 기록으로 변경한다.

대표 기록이 존재하지 않는 세션은 크루 누적 통계에서 제외한다.

---

# 15. 개인 사진과 크루 공유 사진의 조회 방식

## 개인 기록 화면

각 사용자의 개인 기록에서는 본인이 촬영한 사진만 조회한다.

```text
크루장 개인 기록
→ 크루장 사진만 표시

크루원 A 개인 기록
→ 크루원 A 사진만 표시
```

다른 참가자가 찍은 사진은 개인 기록 API에 포함하지 않는다.

---

## 크루 기록 화면

크루 같이 플로깅 기록에서는 해당 세션 참가자들이 촬영한 사진 전체를 조회한다.

사진은 업로더 기준으로 그룹화할 수 있는 형태로 반환한다.

예시:

```text
정아현
- 사진 1
- 사진 2

김플로
- 사진 3

홍길동
- 사진 4
- 사진 5
```

사진 응답에는 최소한 다음 정보를 제공한다.

- 사진 식별자
- `objectUrl`
- 업로더 사용자 식별자
- 업로더 닉네임
- 업로더 프로필 이미지
- 촬영 시각 또는 등록 시각

현재 사진 기능에 촬영 시각 정보가 없다면 기존 모델을 분석한 후 등록 시각을 사용하거나 필요한 최소 필드를 추가한다.

---

# 16. 크루 공유 사진 접근 권한

공유 사진 업로드 권한과 조회 권한을 구분한다.

## 업로드 권한

해당 같이 플로깅 세션에 실제로 참가한 사용자만 공유 사진을 등록할 수 있다.

단순히 해당 크루의 크루원이라는 이유만으로 참가하지 않은 세션에 사진을 추가할 수 없다.

## 조회 권한

현재 해당 크루에 소속된 모든 활성 크루원은 완료된 크루 기록과 공유 사진을 조회할 수 있다.

- 세션에 참가하지 않은 크루원도 조회 가능
- 새롭게 가입한 크루원도 과거 기록과 사진 조회 가능
- 탈퇴한 사용자는 조회 불가
- 탈퇴 후 재가입하면 다시 조회 가능
- 사진 업로더가 탈퇴하더라도 기존 크루 기록의 사진은 유지

현재 `objectUrl`이 공개 S3 URL이라면 API에서는 크루원 여부를 검증할 수 있지만 URL 자체가 외부에 유출된 경우 S3 직접 접근까지 막을 수는 없다.

이번 MVP에서는 기존 S3 공개 정책을 유지할 수 있다.

향후 사진 접근 자체를 엄격히 제한해야 한다면 다음 방식으로 변경할 수 있다.

```text
S3 객체 비공개
→ DB에는 object key 저장
→ 크루원 확인 후 Presigned GET URL 발급
```

이번 구현에서는 기존 프로젝트의 S3 접근 정책을 우선 따른다.

---

# 17. 크루 플로깅 기록 목록

크루 상세 화면에서 완료된 크루 같이 플로깅 기록 목록을 조회한다.

같이 플로깅 활동 한 번당 한 건만 표시한다.

각 기록에는 다음 정보를 제공한다.

- 크루 같이 플로깅 기록 식별자
- 진행 날짜
- 대표 사용자 닉네임
- 대표 기록의 걸음 수
- 대표 기록의 이동 거리
- 대표 기록의 플로깅 시간
- 참가 인원 수
- 공유 사진 수
- 대표 사진 또는 최근 공유 사진

대표 사진은 참가자 전체 공유 사진 중 하나를 사용할 수 있다.

사진이 없다면 기존 기본 이미지를 사용한다.

---

# 18. 크루 플로깅 기록 상세

크루 기록을 선택하면 다음 정보를 제공한다.

- 같이 플로깅 날짜
- 공통 시작 시각
- 공통 종료 시각
- 대표 사용자
- 대표 기록의 걸음 수
- 대표 기록의 이동 거리
- 대표 기록의 플로깅 시간
- 참가자 목록
- 참가 인원 수
- 참가자 전체 공유 사진
- 업로더별 그룹화에 필요한 사용자 정보

다음 정보는 제공하지 않는다.

- 참가자별 이동 경로
- 참가자별 거리
- 참가자별 걸음 수
- 참가자별 플로깅 시간
- 참가자별 경험치
- 참가자별 개인 리포트

---

# 19. 폴링

MVP에서는 신규 실시간 인프라를 도입하지 않는다.

활성 세션 조회 API를 약 2~3초 간격으로 폴링한다.

확인할 상태 변화:

- 참가자 모집
- 참가자 수 변경
- 크루장의 시작
- 크루장의 전체 종료
- 개인 기록 제출 여부
- 크루 기록 완료 여부

폴링 응답에는 다음 정보가 필요하다.

- 활성 세션 존재 여부
- 세션 상태
- 서버 기준 시작 시각
- 서버 기준 종료 시각
- 로그인 사용자의 참가 여부
- 로그인 사용자의 개인 기록 제출 여부
- 참가 인원 수

같은 상태 응답을 여러 번 받아도 화면 이동이나 완료 요청이 중복 실행되지 않도록 프론트엔드에서 방지한다.

백엔드도 중복 요청에 안전해야 한다.

---

# 20. 필수 권한 검증

다음 권한을 반드시 검증한다.

- 크루장이 아닌 사용자는 세션 생성 불가
- 크루장이 아닌 사용자는 세션 시작 불가
- 크루장이 아닌 사용자는 전체 종료 불가
- 크루 소속이 아닌 사용자는 크루 상세 조회 불가
- 크루 소속이 아닌 사용자는 활성 세션 조회 불가
- 크루 소속이 아닌 사용자는 완료된 크루 기록 조회 불가
- 현재 크루원이 아닌 사용자는 공유 사진 조회 불가
- 해당 세션 참가자가 아닌 사용자는 공유 사진 등록 불가
- 다른 사용자의 개인 기록을 대신 저장할 수 없음
- 다른 사용자의 개인 기록과 개인 사진을 조회할 수 없음
- 다른 사용자의 개인 리포트를 조회할 수 없음

모든 사용자 식별은 요청 body의 `userId`가 아니라 기존 인증 정보에서 가져온 로그인 사용자 ID를 기준으로 처리한다.

# 21. 필수 테스트

## 사진 업로드 및 연결

- 기존 업로드 URL API가 같이 플로깅에서도 정상 작동
- 참가자마다 자신의 인증 정보로 업로드 URL 발급
- 동일한 S3 사진을 중복 업로드하지 않고 개인 기록과 크루 기록에서 참조
- 크루장 개인 기록에는 크루장 사진만 저장
- 일반 크루원 개인 기록에는 해당 크루원 사진만 저장
- 크루 기록에는 참가자 전체 사진 표시
- 세션 참가자가 아닌 사용자는 크루 공유 사진 등록 불가
- 현재 크루원 전체가 완료된 크루 공유 사진 조회 가능
- 크루 비회원은 공유 사진 조회 불가
- 동일 완료 요청으로 사진 연결이 중복 생성되지 않음
- 임의의 외부 이미지 URL 등록 차단

## 기록 분리

- 각 참가자의 개인 기록이 독립적으로 저장
- 다른 참가자 사진이 개인 기록에 노출되지 않음
- 크루 기록은 활동 한 번당 한 건만 생성
- 크루 기록 수치는 대표 기록만 사용
- 참가자 전체 거리와 걸음 수를 합산하지 않음
- 크루장 기록을 대표 기록으로 우선 선택
- 크루장 기록이 없으면 가장 먼저 완료한 참가자 기록 선택

## 권한 및 개인정보

- 다른 사용자 개인 기록 조회 불가
- 크루 기록에서 참가자별 거리 노출 안 됨
- 크루 기록에서 참가자별 경로 노출 안 됨
- 크루 기록에서 참가자별 경험치 노출 안 됨
- 크루 기록에서 참가자별 리포트 노출 안 됨
- 대표 개인 기록의 원본 상세를 다른 크루원에게 공개하지 않음

# 22. Codex 구현 지침

먼저 현재 코드베이스를 분석한다.

특히 다음 코드를 확인한다.

- `/api/plogging-sessions/photo/upload-url` Controller 및 Service
- 업로드 URL의 S3 객체 경로 생성 방식
- 응답의 `objectUrl` 사용 위치
- 개인 플로깅 완료 요청 DTO
- 개인 사진이 DB에 저장되는 시점
- 사진 엔티티와 개인 플로깅 세션의 관계
- 중복 사진 방지 방식
- 개인 플로깅 완료 트랜잭션
- 로그인 사용자 ID 주입 방식
- 개인 기록 소유권 검증 방식
- S3 URL 및 파일 형식 검증 방식

구현 전에 다음 내용을 먼저 출력한다.

1. 현재 개인 사진 업로드 전체 흐름
2. 업로드 URL에서 생성되는 S3 경로의 의미
3. `objectUrl`이 DB에 저장되는 시점
4. 기존 사진 로직 중 그대로 재사용할 부분
5. 개인 기록과 크루 기록에서 동일 사진을 참조하는 방법
6. 제안하는 크루 도메인과 관계
7. 추가하거나 수정할 API
8. 추가하거나 수정할 파일 목록
9. 동시성 및 중복 요청 처리 방식
10. 구현 순서

정확한 데이터 구조를 이 명세만 보고 고정하지 않는다.

기존 프로젝트 구조를 분석한 후 가장 자연스러운 방식을 선택한다.

다만 다음 원칙은 반드시 유지한다.

```text
사진 업로드
= 기존 Presigned URL API 재사용

S3 업로드
= 사진 한 장당 한 번만 수행

개인 기록
= 본인 사진만 연결

크루 기록
= 참가자 전체 사진 연결

사진 업로드 권한
= 해당 같이 플로깅 참가자만

사진 조회 권한
= 현재 크루원 전체

크루 기록 수치
= 대표 개인 기록 기준
```

관련 없는 코드를 대규모로 리팩터링하지 않는다.

현재 프로젝트의 코드 스타일, 패키지 구조, 예외 처리와 응답 형식을 유지한다.
