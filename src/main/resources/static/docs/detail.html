프로젝트 개요

Plover는 플로깅(Plogging — 조깅하며 쓰레기 줍기) 활동을 기록·분석하는 백엔드 서비스입니다. 사용자 인증, 플로깅 세션 관리, AI 기반 쓰레기 인식, 주변 시설 조회, 경로 추천 기능을 제공합니다.

OAuth 소셜 로그인

v1 vs v2 방식 비교

v1 — Authorization Code Flowv2 — Native SDK
엔드포인트 POST /api/auth/kakao/login POST /api/auth/v2/kakao/login
요청 파라미터 { code } — 인가 코드 { accessToken } — SDK 발급 토큰
주 사용처 웹 브라우저 / WebView 기반 앱 iOS · Android 네이티브 앱 (카카오 SDK)
서버 → 카카오 통신 횟수 2회 (토큰 교환 + 사용자 정보) 1회 (사용자 정보만)
장점 code는 단회성이라 탈취 후 재사용 불가, 웹 표준 OAuth 흐름 흐름 단순, 서버 왕복 1회 감소, Native SDK UX 자연스러움
단점 서버가 카카오 토큰 서버를 한 번 더 호출 — 레이턴시 증가 클라이언트가 accessToken을 서버로 전송하므로 전송 구간 보안 의존 (HTTPS 필수)
401 에러 처리 KAKAO_TOKEN_FAILED (토큰 교환 실패) KAKAO_TOKEN_INVALID (만료·유효하지 않은 토큰)
상태 Deprecated — Native SDK 전환 완료 후 제거 예정 현행

카카오 로그인 v2 — Native SDK 방식 현행

iOS/Android 카카오 Native SDK에서 직접 발급받은 accessToken을 서버로 전달합니다. 서버-서버 토큰 교환 단계가 없어 구조가 단순합니다.

1

액세스 토큰 수신

클라이언트가 카카오 Native SDK로 직접 발급받은 accessToken을 POST /api/auth/v2/kakao/login으로 전달

2

사용자 정보 조회

전달받은 accessToken으로 https://kapi.kakao.com/v2/user/me 호출 → 이메일, 닉네임, 프로필 이미지 획득

3

Upsert

provider=KAKAO, providerId=카카오ID로 조회 → 없으면 신규 가입, 있으면 기존 반환

4

JWT 발급

LoginResponse { accessToken, tokenType, userId, nickname, email } 반환

401 에러 구분: getKakaoUserInfo() 호출 시 카카오 API가 401을 반환하면 KAKAO_TOKEN_INVALID (만료·유효하지 않은 토큰)를 발생시킵니다. 그 외 카카오 API 오류는 KAKAO_USER_INFO_FAILED로 구분합니다.

카카오 로그인 v1 — Authorization Code Flow Deprecated

WebView 기반 방식. Native SDK 전환 완료 후 제거 예정이며, 하위 호환을 위해 엔드포인트는 유지합니다.

1

인증 코드 수신

클라이언트가 카카오 로그인 후 받은 code를 POST /api/auth/kakao/login으로 전달

2

액세스 토큰 교환

https://kauth.kakao.com/oauth/token에 code 전송 → Kakao Access Token 획득

3

사용자 정보 조회

https://kapi.kakao.com/v2/user/me로 이메일, 닉네임, 프로필 이미지 조회

4

Upsert

5

JWT 발급

Apple 로그인 (JWKS 서명 검증)

1

멀티 OAuth Provider 설계

핵심: provider + provider_id의 복합 유니크 제약으로 동일 숫자 ID가 Kakao와 Apple에 각각 존재할 수 있습니다. 기존 kakao_id (BIGINT, UNIQUE) 단일 컬럼에서 provider (VARCHAR) + provider_id (VARCHAR) 조합으로 마이그레이션했습니다. 
-- DB 유니크 제약 (마이그레이션)
ALTER TABLE users ADD UNIQUE KEY uk_provider_provider_id (provider, provider_id);

-- Entity
@Table(uniqueConstraints = @UniqueConstraint(columnNames = {"provider", "provider_id"}))
public class User {
    @Enumerated(EnumType.STRING)
    @Column(name = "provider", nullable = false, length = 20)
    private OAuthProvider provider;   // KAKAO | APPLE | GOOGLE

    @Column(name = "provider_id", nullable = false)
    private String providerId;
}

// 생성: userId를 subject로
String token = Jwts.builder()
    .subject(String.valueOf(userId))
    .issuedAt(new Date())
    .expiration(new Date(System.currentTimeMillis() + expiration))
    .signWith(secretKey)   // HMAC-SHA
    .compact();

// 검증
Claims claims = Jwts.parser()
    .verifyWith(secretKey)
    .build()
    .parseSignedClaims(token)
    .getPayload();

필터 기반 인증 (JwtAuthenticationFilter)

// OncePerRequestFilter 구현 (Spring Security 없이)
protected void doFilterInternal(HttpServletRequest request, ...) {
    String token = extractBearer(request);   // "Authorization: Bearer ..."

    if (token == null) { chain.doFilter(...); return; }

    if (!jwtProvider.isValid(token)) {
        sendUnauthorized(response, INVALID_TOKEN);
        return;
    }

    Long userId = jwtProvider.getUserId(token);
    request.setAttribute("userId", userId);  // Controller로 전달
    chain.doFilter(...);
}

플로깅 도메인

레벨 · 경험치 · 칭호 시스템

// User.java — 도메인 로직을 엔티티에 캡슐화
private static final long EXP_GRANT_INTERVAL_SECONDS = 5L;    // 5초마다 1경험치
private static final long EXPERIENCE_PER_LEVEL = 720L;         // 1레벨 = 720exp (1시간)

public void addPloggingTimeSeconds(long seconds) {
    this.totalPloggingSeconds += seconds;
    this.experience = (totalPloggingSeconds / EXP_GRANT_INTERVAL_SECONDS);
    this.level = (int)(experience / EXPERIENCE_PER_LEVEL) + 1;
    this.title = UserTitle.of(this.level);   // 레벨 기반 칭호 자동 부여
}

private record로 단일 루프 다중 필드 집계

// 필드마다 스트림을 별도로 순회하는 안티패턴을 방지
private record SessionAggregate(long stepCount, long distanceMeters, long caloriesBurned, long ploggingSeconds) {
    static SessionAggregate from(List<SessionStatsView> sessions) {
        long step = 0, dist = 0, cal = 0, sec = 0;
        for (SessionStatsView s : sessions) {
            step += s.getStepCount();
            dist += s.getDistanceMeters();
            cal  += s.getCaloriesBurned();
            sec  += s.getPloggingSeconds();
        }
        return new SessionAggregate(step, dist, cal, sec);
    }
}

회원 탈퇴 — 트랜잭션 커밋 후 S3 삭제

// deleteUser(): DB 삭제 성공 후에만 S3 이미지 삭제
@Transactional
public void deleteUser(Long userId) {
    String profileImageUrl = user.getProfileImageUrl();

    ploggingPhotoRepository.deleteByPloggingSessionUserId(userId);
    ploggingRoutePointRepository.deleteByPloggingSessionUserId(userId);
    ploggingSessionRepository.deleteByUserId(userId);
    userRepository.delete(user);

    // 트랜잭션 커밋 이후 실행 — DB 롤백 시 S3 삭제 방지
    if (profileImageUrl != null) {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                profileImageStorageService.deleteIfOwnedByBucket(profileImageUrl);
            }
        });
    }
}
afterCommit() 훅을 쓰는 이유: S3 삭제는 되돌릴 수 없습니다. 트랜잭션 내부에서 S3를 먼저 삭제하면 DB 롤백 시 이미지가 사라져 고아 레코드가 됩니다. TransactionSynchronization.afterCommit()으로 DB 커밋이 확정된 뒤에만 S3 삭제를 실행합니다.

ORDER BY distance ASC
ST_Distance_Sphere는 지구를 구로 근사하여 두 좌표 간 거리(미터)를 계산합니다. 반경 1km 시설 검색처럼 높은 정밀도보다 속도가 중요한 경우에 적합합니다. (latitude, longitude)에 공간 인덱스를 걸면 반경 조건 필터링 성능이 향상됩니다.

Caffeine 기반 경로 응답 캐시

항목값의미
저장 위치JVM heap별도 Redis 없이 애플리케이션 프로세스 안에 저장
라이브러리CaffeineJava 인메모리 캐시
최대 엔트리1,000메모리 사용량 상한
TTL5분경로 추천 결과의 짧은 재사용
좌표 버킷0.0005도한국 기준 대략 위도 55m, 경도 44~45m 단위
캐싱 대상성공 응답외부 엔진 실패는 캐시하지 않음
 
private final Cache<RouteCacheKey, RouteDto.Response> routeCache = Caffeine.newBuilder()
    .maximumSize(1_000L)
    .expireAfterWrite(Duration.ofMinutes(5))
    .build();

public RouteDto.Response getRoute(double lat, double lon, int distance, String mode) {
    String normalizedMode = normalizeMode(mode);
    RouteCacheKey key = RouteCacheKey.from(lat, lon, distance, normalizedMode);
    return routeCache.get(key, ignored -> requestRouteFromEngine(lat, lon, distance, normalizedMode));
}

private String normalizeMode(String mode) {
    if (mode == null || mode.isBlank()) return "PLOGGING";
    return mode.trim().toUpperCase(Locale.ROOT);
}

private record RouteCacheKey(long latBucket, long lonBucket, int distance, String mode) {
    private static RouteCacheKey from(double lat, double lon, int distance, String mode) {
        return new RouteCacheKey(toBucket(lat), toBucket(lon), distance, mode);
    }
    private static long toBucket(double coordinate) {
        return Math.round(coordinate / 0.0005);
    }
}
캐시 tradeoff: 아주 가까운 좌표 요청은 같은 추천 경로를 재사용할 수 있습니다. 플로깅 추천 경로에서는 수십 미터 단위의 근접 위치를 같은 요청으로 묶어도 사용자 경험상 수용 가능하다고 보고, 외부 Route Engine 반복 호출 비용을 크게 줄이는 쪽을 택했습니다.

성능 개선: Route API 병목 완화

문제 상황

k6 stress 테스트에서 GET /api/v1/routes가 주요 병목으로 확인되었습니다. 제한된 위치 데이터를 반복 사용하는 부하 테스트 특성상 동일하거나 매우 유사한 좌표 요청이 많았고, 기존 구조는 매 요청마다 외부 Route Engine을 호출했습니다.

개선 방향

1

반복 호출 원인 확인

비슷한 위도/경도, 같은 시간, 같은 mode 요청이 외부 Route Engine으로 반복 전달되는 구조를 확인했습니다.

2

요청 key 정규화

mode는 대문자와 기본값으로 정규화하고, 좌표는 0.0005도 버킷으로 묶어 캐시 적중률을 높였습니다.

3

성공 응답만 캐시

외부 엔진 실패 응답은 캐시하지 않아 일시 장애가 5분 동안 고정되는 상황을 피했습니다.

결론: 병목은 Spring Boot 내부 계산보다 외부 Route Engine 반복 호출 비용에 가까웠습니다. Caffeine 캐시 적용 후 동일/유사 좌표가 반복되는 상황에서 route API p95가 3149.45ms에서 35.64ms로 낮아졌습니다. 단, 실제 운영 트래픽에서 모든 좌표가 매번 크게 다르면 캐시 적중률에 따라 개선 폭은 달라집니다.

// 허용 형식: JPEG, PNG (10MB, 2000만 픽셀 이하)
// 3단계 검증: Content-Type + 확장자 → Magic Number → ImageReader 헤더

public void validate(MultipartFile image) {
    if (image.getSize() > 10 * 1024 * 1024L)
        throw new PloggingException(IMAGE_SIZE_EXCEEDED);

    ImageFormat ctFormat  = ImageFormat.fromContentType(image.getContentType());
    ImageFormat extFormat = ImageFormat.fromFilename(image.getOriginalFilename());
    if (ctFormat == null || extFormat == null || ctFormat != extFormat)
        throw new PloggingException(INVALID_IMAGE_FORMAT);

    // Magic Number: JPEG = FF D8 FF, PNG = 89 50 4E 47 0D 0A 1A 0A
    // ImageReader로 width * height > 20_000_000 픽셀이면 거부
    validateImageContent(image, ctFormat);
}
3단계 검증 이유: Content-Type과 확장자는 클라이언트가 임의로 조작할 수 있습니다. Magic Number(파일 헤더 바이트)를 실제로 읽어 파일 형식을 확인하고, ImageReader로 헤더를 파싱해 픽셀 수까지 검증하면 위장 파일을 차단할 수 있습니다.

Q카카오와 Apple 로그인의 구현 방식 차이는?
카카오 v2 (현행, Native SDK)는 클라이언트가 카카오 Native SDK로 직접 발급받은 accessToken을 서버로 전달합니다. 서버는 그 토큰으로 카카오 사용자 정보 API를 바로 호출합니다. 서버-서버 토큰 교환 단계가 없어 흐름이 단순합니다.

카카오 v1 (Deprecated, Authorization Code Flow)는 WebView 기반입니다. 클라이언트에서 받은 code로 서버가 카카오 토큰 서버에 액세스 토큰을 요청하고, 그 토큰으로 사용자 정보 API를 호출합니다. Native SDK 전환 완료 후 제거 예정입니다.

Apple은 identityToken(JWT) 검증 방식입니다. Apple의 JWKS 엔드포인트에서 공개키를 가져와 identityToken의 RSA 서명을 검증하고, Claims의 iss/aud/sub를 확인합니다. 추가 API 호출 없이 토큰 자체에서 사용자 정보를 추출합니다.
Q카카오 로그인에 v2 엔드포인트를 별도로 추가한 이유는?
기존 v1은 WebView에서 인가 code를 받아 서버가 카카오 토큰 서버와 한 번 더 통신하는 구조입니다. 모바일 앱을 카카오 Native SDK로 전환하면 SDK가 accessToken을 직접 발급하므로, code 방식 대신 accessToken을 그대로 서버에 넘기는 것이 자연스럽습니다.

기존 엔드포인트(/api/auth/kakao/login)를 수정하지 않고 v2를 별도 추가한 이유는 하위 호환 유지입니다. 앱 업데이트가 즉시 전체 사용자에게 배포되지 않으므로 이전 버전 클라이언트가 기존 엔드포인트를 계속 호출합니다. 두 엔드포인트를 병행 운영하다 Native SDK 전환이 완료되면 v1을 제거할 계획입니다.

또한 KAKAO_TOKEN_INVALID 에러코드를 신규 추가해, accessToken이 만료됐을 때(401 응답)와 그 외 카카오 API 오류(KAKAO_USER_INFO_FAILED)를 명확히 구분합니다.
Q카카오 로그인 v1(Code 방식)과 v2(Native SDK 방식)의 사용처와 장단점 차이는?
v1 — Authorization Code Flow는 웹 브라우저나 WebView 기반 앱에서 사용합니다. 카카오가 발급한 인가 code를 클라이언트가 서버로 넘기면, 서버가 카카오 토큰 서버에 code를 보내 accessToken으로 교환한 뒤 사용자 정보 API를 호출합니다. 즉 서버 → 카카오 통신이 2회 발생합니다.

장점은 code가 단회성(one-time)이라 네트워크에서 탈취돼도 재사용이 불가능하다는 점입니다. 단점은 토큰 교환 왕복이 추가되어 레이턴시가 늘고 구현이 복잡합니다.

v2 — Native SDK 방식은 iOS·Android 네이티브 앱에서 사용합니다. 카카오 SDK가 accessToken을 클라이언트에서 직접 발급하고, 그 토큰을 서버로 전달하면 서버는 사용자 정보 API 호출 1회만 수행합니다.

장점은 흐름이 단순하고 서버 왕복이 1회 줄어 레이턴시가 개선되며, Native SDK의 UX(카카오톡 앱 연동 등)를 그대로 활용할 수 있습니다. 단점은 accessToken을 클라이언트에서 서버로 전송하는 구간의 보안이 HTTPS에 의존한다는 점과, 토큰이 만료된 경우 클라이언트가 SDK로 재발급 후 재요청해야 한다는 점입니다. 이를 위해 만료 시 KAKAO_TOKEN_INVALID(401)를 반환해 클라이언트가 상황을 명확히 인지할 수 있게 했습니다.
Qprovider + provider_id 복합 유니크를 쓴 이유는?
카카오 사용자 ID 12345와 Apple 사용자 ID 12345는 완전히 다른 사람입니다. provider_id만 단독으로 UNIQUE를 걸면 두 사람 중 한 명이 가입할 수 없습니다. (provider, provider_id) 복합 유니크로 제공자별로 사용자를 구분하면 Kakao·Apple·Google이 각각 독립적인 ID 공간을 가질 수 있습니다.
QJWT를 Spring Security 없이 구현한 방법은?
OncePerRequestFilter를 직접 구현한 JwtAuthenticationFilter가 Authorization 헤더에서 토큰을 추출·검증하고, 유효한 경우 request.setAttribute("userId", userId)로 저장합니다. Controller에서는 HandlerMethodArgumentResolver를 구현한 LoginUserIdArgumentResolver가 @LoginUserId 어노테이션을 감지해 request attribute에서 userId를 꺼내 주입합니다.
QS3에 파일을 직접 받지 않고 Presigned URL을 쓰는 이유는?
서버가 파일을 받으면 대용량 파일이 서버 메모리와 네트워크를 점유합니다. Presigned URL 방식은 서버가 S3에 서명된 임시 URL을 발급하고, 클라이언트가 그 URL로 S3에 직접 PUT 업로드합니다. 서버는 URL 발급과 DB 저장만 처리하므로 서버 부하를 줄이고 S3 대역폭을 직접 활용합니다. URL은 10분 유효하며 Content-Type 헤더가 서명에 포함됩니다. 다만 S3가 파일 내부 바이트까지 검증하는 것은 아니므로, 서버가 직접 파일을 받는 AI 분석 API에서는 별도의 Magic Number와 이미지 헤더 검증을 수행합니다.
QPage 대신 Slice를 쓴 이유는?
Page는 전체 레코드 수를 위한 COUNT 쿼리를 추가로 실행합니다. 플로깅 기록 목록처럼 "다음 페이지 있음/없음"만 필요한 경우엔 COUNT가 불필요한 비용입니다. Slice는 hasNext()만 제공하고 COUNT를 실행하지 않아 성능상 유리합니다.
QJPQL 집계 쿼리에서 인터페이스 Projection을 쓴 이유는?
엔티티 전체를 로드하면 불필요한 컬럼까지 DB에서 가져와 메모리를 낭비합니다. 인터페이스 기반 Projection은 필요한 집계 필드만 선언하면 JPA가 SELECT 절을 해당 필드로 한정합니다. Repository 내부 중첩 인터페이스로 선언해 응집도를 높였습니다. SUM이 레코드 없을 때 null을 반환하므로 COALESCE로 0 처리했습니다.
QAI 분석을 @Async로 처리한 이유는?
AI 이미지 분석은 외부 서버 호출로 수 초가 소요될 수 있습니다. 동기로 처리하면 클라이언트가 그만큼 대기해야 합니다. 컨트롤러에서는 이미지 검증과 byte 배열 변환까지만 수행하고, @Async("aiAnalysisExecutor")로 외부 AI 서버 호출과 DB 저장을 별도 스레드풀에서 처리합니다. 분석 접수 응답은 바로 반환하고, ThreadPoolTaskExecutor는 코어 2개, 최대 5개, 큐 100으로 제한했습니다.
QRoute Engine 병목을 Caffeine 캐시로 줄인 방식은?
GET /api/v1/routes는 사용자의 현재 위치, 목표 시간, mode를 받아 외부 Route Engine에 추천 경로를 요청하는 API입니다. k6 stress 테스트에서 병목은 Spring 내부 계산보다 외부 Route Engine 반복 호출에 가까웠습니다.

개선은 성공 응답만 JVM 인메모리 Caffeine 캐시에 저장하는 방식입니다. cache key는 위도·경도를 0.0005도 단위로 버킷화하고, 앱의 time 값은 (time / 60.0) * 5000으로 거리(m)로 변환한 값과 mode 정규화 결과를 함께 사용합니다. 실패 응답은 캐시하지 않으므로 일시 장애 결과가 재사용되지 않습니다.

정책은 최대 1000개, write 후 5분 만료입니다. 좌표 버킷은 대략 위도 55m, 서울권 경도 44~45m 정도라 매우 가까운 위치의 반복 요청을 묶을 수 있습니다. 적용 후 route API p95가 3149.45ms에서 35.64ms로 낮아져 반복 호출 상황에서 효과가 컸습니다.
Q예외 처리를 ErrorCode 인터페이스 + BusinessException 구조로 설계한 이유는?
IllegalArgumentException 같은 표준 예외를 직접 던지면 GlobalExceptionHandler에서 HTTP 상태 코드와 메시지를 구분할 수 없습니다. ErrorCode 인터페이스에 getStatus()와 getMessage()를 정의하고 도메인별 enum이 구현합니다. BusinessException이 ErrorCode를 포함하면 GlobalExceptionHandler 한 곳에서 모든 도메인 예외를 일관되게 처리할 수 있습니다.
QST_Distance_Sphere를 쓴 이유와 한계는?
MySQL 내장 공간 함수로 두 좌표 간 거리를 미터 단위로 계산합니다. 지구를 완전한 구로 근사하기 때문에 정확도는 0.5% 내외입니다. 반경 1km 시설 검색처럼 정밀도보다 속도가 중요한 경우에 적합합니다. 한계는 지구가 타원체이므로 장거리에서 오차가 커진다는 점이며, 더 정밀한 거리가 필요하면 Haversine 공식이나 PostGIS를 고려해야 합니다.
Q생성자 주입만 사용하는 이유는?
필드 주입(@Autowired)은 리플렉션으로 주입되므로 테스트 시 Mock 주입이 어렵고, 의존성이 외부에 보이지 않습니다. 생성자 주입은 의존성이 명시적이고 final 선언이 가능하며, 테스트에서 new로 직접 생성할 수 있습니다. 순환 의존성도 컴파일 타임에 감지됩니다. Lombok의 @RequiredArgsConstructor로 보일러플레이트를 제거했습니다.
QDTO에 Java Record를 사용한 이유는?
Java 16+ Record는 불변 데이터 클래스를 간결하게 선언합니다. equals, hashCode, toString, 생성자가 자동 생성됩니다. DTO는 데이터 전송 목적의 단순 구조체라 가변 상태가 필요 없어 Record가 이상적입니다. Outer class + Inner Record 패턴으로 관련 Request/Response DTO를 그룹핑해 응집도를 높였습니다.
Q엔티티에 setter를 두지 않고 도메인 메서드를 쓴 이유는?
public setter는 어디서든 엔티티 상태를 변경할 수 있어 일관성을 보장하기 어렵습니다. 예를 들어 플로깅 시간이 추가될 때 단순히 setTotalPloggingSeconds()로 값을 바꾸면 경험치와 레벨·칭호 갱신을 빠뜨릴 수 있습니다. addPloggingTimeSeconds() 같은 도메인 메서드는 연관된 모든 상태 변경을 한 곳에서 처리하므로 불변식을 보장합니다.
Q회원 탈퇴 시 S3 이미지 삭제를 트랜잭션 커밋 이후에 처리한 이유는?
S3 삭제는 되돌릴 수 없는 외부 작업입니다. 트랜잭션 내부에서 S3를 먼저 삭제하고 DB가 롤백되면 이미지는 사라졌는데 DB에는 URL이 남는 고아 데이터가 생깁니다. 반대로 DB를 먼저 삭제하고 S3 실패 시에는 DB를 롤백할 수 없어 불일치가 발생합니다.

TransactionSynchronizationManager.registerSynchronization()의 afterCommit() 훅을 사용하면 DB 트랜잭션 커밋이 확정된 이후에만 S3 삭제가 실행됩니다. DB 커밋 실패 시에는 S3 삭제가 아예 호출되지 않으므로 일관성을 보장합니다. S3 삭제 자체가 실패하더라도 회원 탈퇴 응답에는 영향을 주지 않도록 예외를 전파하지 않습니다.
QAI 분석 이미지 검증을 3단계로 설계한 이유는?
Content-Type과 파일 확장자는 클라이언트가 임의로 조작할 수 있어 단독으로 신뢰하지 않습니다. 현재 검증은 빈 파일 여부, 10MB 크기 제한, Content-Type과 확장자 일치, Magic Number, ImageReader 헤더 파싱, 픽셀 수 2000만 제한 순서로 진행됩니다.

Magic Number 검증에서는 파일의 실제 첫 바이트를 읽어 JPEG(FF D8 FF)와 PNG(89 50 4E 47 ...)의 고정 헤더를 확인합니다. 이후 ImageReader가 실제 이미지로 파싱 가능한지, reader가 판단한 포맷이 기대 포맷과 같은지, width/height가 정상인지 확인합니다. 픽셀 제한은 작은 파일처럼 보이지만 디코딩 시 큰 메모리를 쓰는 이미지 폭탄을 막기 위한 방어입니다. AI 분석 API는 JPEG와 PNG만 허용하고, 일반 S3 presigned 업로드는 별도로 webp/heic/heif/avif까지 허용합니다.
QFilter와 Interceptor의 차이는? 언제 각각을 쓰나요?
Filter는 Servlet 레벨에서 동작합니다. Spring 컨텍스트 밖에 위치해 어느 Controller로 가는 요청인지 알 수 없고, 모든 요청에 적용됩니다. JWT 검증, CORS 처리처럼 Spring과 무관하게 전처리해야 하는 작업에 적합합니다.

Interceptor는 DispatcherServlet 이후 Spring MVC 레벨에서 동작합니다. 어느 Controller, 어느 메서드로 가는 요청인지 알 수 있고 preHandle / postHandle / afterCompletion 3단계를 제공합니다. 특정 URL 패턴에만 다른 인증을 적용하거나 (예: /admin/** 관리자 권한 체크), API 응답 시간 측정처럼 Spring 컨텍스트 정보가 필요한 횡단 관심사에 적합합니다.

이 프로젝트에서 JWT 검증을 Filter로 구현한 이유는 Spring과 무관하게 모든 요청에 먼저 적용해야 하고, filterChain.doFilter(request, ...)로 동일한 request 객체를 다음 단계로 전달해 request.setAttribute("userId", ...)가 Controller까지 살아있기 때문입니다.
