프로젝트 개요

Flover는 플로깅(Plogging — 조깅하며 쓰레기 줍기) 활동을 기록·분석하는 백엔드 서비스입니다. 사용자 인증, 플로깅 세션 관리, AI 기반 쓰레기 인식, 주변 시설 조회, 경로 추천 기능을 제공합니다.

👤

User 도메인

OAuth 소셜 로그인 (Kakao · Apple), JWT 인증, 레벨·칭호 시스템

🏃

Plogging 도메인

세션 기록, 경로 좌표, 인증샷, 월간·주간 통계

🗑️

Facility 도메인

반경 1km 내 화장실·쓰레기통 조회 (공간 인덱스)

🗺️

Route 도메인

외부 라우팅 엔진 연동, 3회 재시도, 경로 추천

요청 처리 흐름

HTTP Request
  → JwtAuthenticationFilter   (토큰 검증, userId → request.setAttribute)
  → Controller                (@LoginUserId Long userId 자동 주입)
  → Service                   (비즈니스 로직)
  → Repository                (DB 조회 / 저장)
  → DTO 변환 후 응답

에러 발생 시:
  BusinessException → GlobalExceptionHandler → ErrorResponse { status, message }

OAuth 소셜 로그인

카카오 로그인 (Authorization Code Flow)

1

인증 코드 수신

클라이언트가 카카오 로그인 후 받은 code를 POST /api/auth/kakao/login으로 전달

2

액세스 토큰 교환

https://kauth.kakao.com/oauth/token에 code 전송 → Kakao Access Token 획득

3

사용자 정보 조회

https://kapi.kakao.com/v2/user/me로 이메일, 닉네임, 프로필 이미지 조회

4

Upsert

provider=KAKAO, providerId=카카오ID로 조회 → 없으면 신규 가입, 있으면 기존 반환

5

JWT 발급

LoginResponse { accessToken, tokenType, userId, nickname, email } 반환

Apple 로그인 (JWKS 서명 검증)

1

identityToken 수신

클라이언트가 Apple 로그인 후 받은 identityToken (JWT)을 전달

2

JWKS 공개키 페칭

https://appleid.apple.com/auth/keys에서 공개키 목록 조회, kid로 매칭

3

RSA 서명 검증

공개키로 identityToken의 서명 검증 (위변조 방지)

4

Claims 검증

iss (appleid.apple.com), aud (clientId), sub (Apple User ID) 유효성 확인

5

Upsert → JWT 발급

provider=APPLE, providerId=sub로 사용자 조회/생성 후 JWT 반환

멀티 OAuth Provider 설계

핵심: provider + provider_id의 복합 유니크 제약으로 동일 숫자 ID가 Kakao와 Apple에 각각 존재할 수 있습니다. 기존 kakao_id (BIGINT, UNIQUE) 단일 컬럼에서 provider (VARCHAR) + provider_id (VARCHAR) 조합으로 마이그레이션했습니다. 
-- DB 유니크 제약 (마이그레이션)
ALTER TABLE users ADD UNIQUE KEY uk_provider_provider_id (provider, provider_id);

-- Entity
@Table(uniqueConstraints = @UniqueConstraint(columnNames = {"provider", "provider_id"}))
public class User {
    @Enumerated(EnumType.STRING)
    @Column(name = "provider", nullable = false, length = 20)
    private OAuthProvider provider;   // KAKAO | APPLE | GOOGLE

    @Column(name = "provider_id", nullable = false)
    private String providerId;
}

JWT 인증

토큰 생성 · 검증 (JwtProvider)

// 생성: userId를 subject로
String token = Jwts.builder()
    .subject(String.valueOf(userId))
    .issuedAt(new Date())
    .expiration(new Date(System.currentTimeMillis() + expiration))
    .signWith(secretKey)   // HMAC-SHA
    .compact();

// 검증
Claims claims = Jwts.parser()
    .verifyWith(secretKey)
    .build()
    .parseSignedClaims(token)
    .getPayload();

필터 기반 인증 (JwtAuthenticationFilter)

// OncePerRequestFilter 구현 (Spring Security 없이)
protected void doFilterInternal(HttpServletRequest request, ...) {
    String token = extractBearer(request);   // "Authorization: Bearer ..."

    if (token == null) { chain.doFilter(...); return; }

    if (!jwtProvider.isValid(token)) {
        sendUnauthorized(response, INVALID_TOKEN);
        return;
    }

    Long userId = jwtProvider.getUserId(token);
    request.setAttribute("userId", userId);  // Controller로 전달
    chain.doFilter(...);
}

S3 파일 업로드 (Presigned URL)

서버가 파일을 직접 받지 않습니다. 클라이언트가 S3에 직접 PUT 업로드하고, 서버는 URL만 DB에 저장합니다. 서버 메모리·네트워크 부하를 줄이는 핵심 설계입니다.
1

Presigned URL 발급 요청

GET /api/users/me/profile-image/upload-url?contentType=image/png

2

서버 → S3 서명

S3Presigner로 10분 유효 PUT URL 생성. Content-Type이 서명에 고정되어 다른 타입 업로드 불가.

3

응답

{ uploadUrl, objectUrl } 반환

4

클라이언트 → S3 직접 업로드

PUT {uploadUrl} with 파일 바이너리

5

URL 저장

PUT /api/users/me/profile-image { imageUrl } → DB 저장 + 이전 이미지 S3에서 삭제

플로깅 도메인

레벨 · 경험치 · 칭호 시스템

// User.java — 도메인 로직을 엔티티에 캡슐화
private static final long EXP_GRANT_INTERVAL_SECONDS = 5L;    // 5초마다 1경험치
private static final long EXPERIENCE_PER_LEVEL = 720L;         // 1레벨 = 720exp (1시간)

public void addPloggingTimeSeconds(long seconds) {
    this.totalPloggingSeconds += seconds;
    this.experience = (totalPloggingSeconds / EXP_GRANT_INTERVAL_SECONDS);
    this.level = (int)(experience / EXPERIENCE_PER_LEVEL) + 1;
    this.title = UserTitle.of(this.level);   // 레벨 기반 칭호 자동 부여
}

private record로 단일 루프 다중 필드 집계

// 필드마다 스트림을 별도로 순회하는 안티패턴을 방지
private record SessionAggregate(long stepCount, long distanceMeters, long caloriesBurned, long ploggingSeconds) {
    static SessionAggregate from(List<SessionStatsView> sessions) {
        long step = 0, dist = 0, cal = 0, sec = 0;
        for (SessionStatsView s : sessions) {
            step += s.getStepCount();
            dist += s.getDistanceMeters();
            cal  += s.getCaloriesBurned();
            sec  += s.getPloggingSeconds();
        }
        return new SessionAggregate(step, dist, cal, sec);
    }
}

주변 시설 검색

MySQL 공간 함수 기반 반경 검색

-- Native Query (ST_Distance_Sphere)
SELECT id, name, road_address, latitude, longitude, trash_type,
       ST_Distance_Sphere(POINT(longitude, latitude), POINT(:lng, :lat)) AS distance
FROM trash_bins
WHERE ST_Distance_Sphere(POINT(longitude, latitude), POINT(:lng, :lat)) <= 1000
ORDER BY distance ASC
ST_Distance_Sphere는 지구를 구로 근사하여 두 좌표 간 거리(미터)를 계산합니다. 반경 1km 시설 검색처럼 높은 정밀도보다 속도가 중요한 경우에 적합합니다. (latitude, longitude)에 공간 인덱스를 걸면 반경 조건 필터링 성능이 향상됩니다.

예외 처리 구조

// 1. ErrorCode 인터페이스 (global/exception/)
public interface ErrorCode {
    HttpStatus getStatus();
    String getMessage();
}

// 2. 공통 에러코드
public enum CommonErrorCode implements ErrorCode {
    INTERNAL_SERVER_ERROR(HttpStatus.INTERNAL_SERVER_ERROR, "서버 내부 오류가 발생했습니다."),
    INVALID_IMAGE_TYPE(HttpStatus.BAD_REQUEST, "지원하지 않는 이미지 형식입니다.");
}

// 3. 도메인 에러코드 (각 도메인의 exception/ 패키지)
public enum UserErrorCode implements ErrorCode {
    USER_NOT_FOUND(HttpStatus.NOT_FOUND, "존재하지 않는 사용자입니다."),
    NICKNAME_ALREADY_USED(HttpStatus.CONFLICT, "이미 사용 중인 닉네임입니다.");
}

// 4. BusinessException (global) — ErrorCode를 포함
public class BusinessException extends RuntimeException {
    private final ErrorCode errorCode;
}

// 5. 도메인 예외 — BusinessException 상속
public class UserException extends BusinessException {
    public UserException(ErrorCode errorCode) { super(errorCode); }
}

// 6. GlobalExceptionHandler (@RestControllerAdvice)
@ExceptionHandler(BusinessException.class)
public ResponseEntity<ErrorResponse> handle(BusinessException e) {
    ErrorCode code = e.getErrorCode();
    return ResponseEntity.status(code.getStatus())
        .body(new ErrorResponse(code.getStatus().value(), code.getMessage()));
}
핵심 원칙: 표준 Java 예외(IllegalArgumentException 등)를 도메인 로직에서 직접 던지지 않습니다. 모든 예외는 BusinessException 서브클래스로 통일되어 GlobalExceptionHandler 한 곳에서 처리됩니다.

면접 예상 질문 & 답변

Q카카오와 Apple 로그인의 구현 방식 차이는?
카카오는 Authorization Code Flow입니다. 클라이언트에서 받은 code로 서버가 카카오 토큰 서버에 액세스 토큰을 요청하고, 그 토큰으로 사용자 정보 API를 호출합니다.

Apple은 identityToken(JWT) 검증 방식입니다. Apple의 JWKS 엔드포인트에서 공개키를 가져와 identityToken의 RSA 서명을 검증하고, Claims의 iss/aud/sub를 확인합니다. 카카오처럼 추가 API를 호출하지 않고 토큰 자체에서 사용자 정보를 추출합니다.
Qprovider + provider_id 복합 유니크를 쓴 이유는?
카카오 사용자 ID 12345와 Apple 사용자 ID 12345는 완전히 다른 사람입니다. provider_id만 단독으로 UNIQUE를 걸면 두 사람 중 한 명이 가입할 수 없습니다. (provider, provider_id) 복합 유니크로 제공자별로 사용자를 구분하면 Kakao·Apple·Google이 각각 독립적인 ID 공간을 가질 수 있습니다.
QJWT를 Spring Security 없이 구현한 방법은?
OncePerRequestFilter를 직접 구현한 JwtAuthenticationFilter가 Authorization 헤더에서 토큰을 추출·검증하고, 유효한 경우 request.setAttribute("userId", userId)로 저장합니다. Controller에서는 HandlerMethodArgumentResolver를 구현한 LoginUserIdArgumentResolver가 @LoginUserId 어노테이션을 감지해 request attribute에서 userId를 꺼내 주입합니다.
QS3에 파일을 직접 받지 않고 Presigned URL을 쓰는 이유는?
서버가 파일을 받으면 대용량 파일이 서버 메모리와 네트워크를 점유합니다. Presigned URL 방식은 서버가 S3에 서명된 임시 URL을 발급하고, 클라이언트가 그 URL로 S3에 직접 PUT 업로드합니다. 서버는 URL 발급과 DB 저장만 처리하므로 서버 부하를 줄이고 S3 대역폭을 직접 활용합니다. URL은 10분 유효하며 Content-Type이 서명에 고정돼 다른 파일 타입 업로드가 불가합니다.
QPage 대신 Slice를 쓴 이유는?
Page는 전체 레코드 수를 위한 COUNT 쿼리를 추가로 실행합니다. 플로깅 기록 목록처럼 "다음 페이지 있음/없음"만 필요한 경우엔 COUNT가 불필요한 비용입니다. Slice는 hasNext()만 제공하고 COUNT를 실행하지 않아 성능상 유리합니다.
QJPQL 집계 쿼리에서 인터페이스 Projection을 쓴 이유는?
엔티티 전체를 로드하면 불필요한 컬럼까지 DB에서 가져와 메모리를 낭비합니다. 인터페이스 기반 Projection은 필요한 집계 필드만 선언하면 JPA가 SELECT 절을 해당 필드로 한정합니다. Repository 내부 중첩 인터페이스로 선언해 응집도를 높였습니다. SUM이 레코드 없을 때 null을 반환하므로 COALESCE로 0 처리했습니다.
QAI 분석을 @Async로 처리한 이유는?
AI 이미지 분석은 외부 서버 호출로 수 초가 소요됩니다. 동기로 처리하면 클라이언트가 그만큼 대기해야 합니다. @Async("aiAnalysisExecutor")로 별도 스레드풀에서 비동기 실행하면 플로깅 완료 응답을 즉시 반환하고, 분석은 백그라운드에서 처리됩니다. ThreadPoolTaskExecutor를 직접 정의해 코어 2개, 최대 5개, 큐 100으로 제어했습니다.
Q예외 처리를 ErrorCode 인터페이스 + BusinessException 구조로 설계한 이유는?
IllegalArgumentException 같은 표준 예외를 직접 던지면 GlobalExceptionHandler에서 HTTP 상태 코드와 메시지를 구분할 수 없습니다. ErrorCode 인터페이스에 getStatus()와 getMessage()를 정의하고 도메인별 enum이 구현합니다. BusinessException이 ErrorCode를 포함하면 GlobalExceptionHandler 한 곳에서 모든 도메인 예외를 일관되게 처리할 수 있습니다.
QST_Distance_Sphere를 쓴 이유와 한계는?
MySQL 내장 공간 함수로 두 좌표 간 거리를 미터 단위로 계산합니다. 지구를 완전한 구로 근사하기 때문에 정확도는 0.5% 내외입니다. 반경 1km 시설 검색처럼 정밀도보다 속도가 중요한 경우에 적합합니다. 한계는 지구가 타원체이므로 장거리에서 오차가 커진다는 점이며, 더 정밀한 거리가 필요하면 Haversine 공식이나 PostGIS를 고려해야 합니다.
Q생성자 주입만 사용하는 이유는?
필드 주입(@Autowired)은 리플렉션으로 주입되므로 테스트 시 Mock 주입이 어렵고, 의존성이 외부에 보이지 않습니다. 생성자 주입은 의존성이 명시적이고 final 선언이 가능하며, 테스트에서 new로 직접 생성할 수 있습니다. 순환 의존성도 컴파일 타임에 감지됩니다. Lombok의 @RequiredArgsConstructor로 보일러플레이트를 제거했습니다.
QDTO에 Java Record를 사용한 이유는?
Java 16+ Record는 불변 데이터 클래스를 간결하게 선언합니다. equals, hashCode, toString, 생성자가 자동 생성됩니다. DTO는 데이터 전송 목적의 단순 구조체라 가변 상태가 필요 없어 Record가 이상적입니다. Outer class + Inner Record 패턴으로 관련 Request/Response DTO를 그룹핑해 응집도를 높였습니다.
Q엔티티에 setter를 두지 않고 도메인 메서드를 쓴 이유는?
public setter는 어디서든 엔티티 상태를 변경할 수 있어 일관성을 보장하기 어렵습니다. 예를 들어 플로깅 시간이 추가될 때 단순히 setTotalPloggingSeconds()로 값을 바꾸면 경험치와 레벨·칭호 갱신을 빠뜨릴 수 있습니다. addPloggingTimeSeconds() 같은 도메인 메서드는 연관된 모든 상태 변경을 한 곳에서 처리하므로 불변식을 보장합니다.
QFilter와 Interceptor의 차이는? 언제 각각을 쓰나요?
Filter는 Servlet 레벨에서 동작합니다. Spring 컨텍스트 밖에 위치해 어느 Controller로 가는 요청인지 알 수 없고, 모든 요청에 적용됩니다. JWT 검증, CORS 처리처럼 Spring과 무관하게 전처리해야 하는 작업에 적합합니다.

Interceptor는 DispatcherServlet 이후 Spring MVC 레벨에서 동작합니다. 어느 Controller, 어느 메서드로 가는 요청인지 알 수 있고 preHandle / postHandle / afterCompletion 3단계를 제공합니다. 특정 URL 패턴에만 다른 인증을 적용하거나 (예: /admin/** 관리자 권한 체크), API 응답 시간 측정처럼 Spring 컨텍스트 정보가 필요한 횡단 관심사에 적합합니다.

이 프로젝트에서 JWT 검증을 Filter로 구현한 이유는 Spring과 무관하게 모든 요청에 먼저 적용해야 하고, filterChain.doFilter(request, ...)로 동일한 request 객체를 다음 단계로 전달해 request.setAttribute("userId", ...)가 Controller까지 살아있기 때문입니다.
